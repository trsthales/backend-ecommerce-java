# RFC-001: Arquitetura Canônica, Invariantes e Modelo Transacional do E-Commerce Backend Reference

- **Status:** APROVADO (CONSTITUCIONAL)
- **Versão:** 2.0 (Consolidada com Mecânicas de Enforcement e Revisão de Pares)
- **Data:** 2026-08-29
- **Autor:** Tech Lead / Core Architecture Team
- **Stack Base:** Java 21 (LTS), Spring Boot 3.4+, Spring Modulith, PostgreSQL 16+, Flyway, Testcontainers, Redis, MapStruct.
- **Rastreabilidade:** `PactX-Core-Baseline` / Invariantes `INV-001` a `INV-007`.

---

## 1. Contexto e Motivação

A maioria das implementações de e-commerce degrada-se em arquiteturas anêmicas (*CRUD controllers* sobrecarregados) ou adota complexidade acidental prematura (microsserviços fragmentados sem fronteiras de domínio maduras).

Esta RFC estabelece a especificação formal de um **Modular Monolith de Alta Performance e Rigor Transacional**, concebido como um **Template de Engenharia de Referência de Nível Industrial**. O projeto prioriza **consistência estrita em operações financeiras e de estoque, concorrência determinística, idempotência universal à prova de crash, integridade contábil imutável e isolamento rígido entre módulos**.

---

## 2. Invariantes Arquiteturais Canônicas

O sistema é governado por 7 invariantes fundamentais invioláveis:

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                                INVARIANTES DO SISTEMA                                  │
├────────────┬───────────────────────────────────────────────────────────────────────────┤
│  INV-001   │ Uma ordem só pode transicionar para paga (PAID) exatamente uma vez.      │
│  INV-002   │ Nenhuma operação pode gerar saldo físico de estoque negativo.             │
│  INV-003   │ Mutações críticas e ingestão de webhooks são universalmente idempotentes.│
│  INV-004   │ OrderItem é um snapshot imutável com rateio pro-rata sem perda de centavos│
│  INV-005   │ Transições de estado do Pedido e Pagamento são monotônicas e estritas.    │
│  INV-006   │ Isolamento total: nenhum módulo acessa tabelas ou repositórios alheios.   │
│  INV-007   │ available_stock = physical_stock - active_reserved_stock (0 <= res <= phy)│
└────────────┴───────────────────────────────────────────────────────────────────────────┘
```

## 3. Matriz Constitucional de Enforcement

Cada invariante é sustentada por mecanismos redundantes em múltiplas camadas de defesa:

| Invariante | Regra de Negócio | Enforcement no Banco de Dados | Enforcement em Código (Java 21) | Teste Mandatório (CI/CD) |
| :--- | :--- | :--- | :--- | :--- |
| **INV-001** | Pedido pago exatamente 1x | `UNIQUE(order_id, status)` na auditoria + `@Version` | SQL Condicional (`UPDATE ... WHERE status = 'PAYMENT_PENDING'`) | 10 webhooks concorrentes disputando o mesmo pedido |
| **INV-002** | Saldo físico $\ge 0$ | `CHECK (physical_quantity >= 0)` | Pessimistic Lock (`SELECT ... FOR UPDATE`) | 20 threads simultâneas disputando 1 unidade física |
| **INV-003** | Idempotência e Crash Recovery | `UNIQUE(idempotency_key)` com `lease_timeout` | Interceptor transacional com atomicidade acoplada ao payload | Replay de requisições e simulação de crash com lease recovery |
| **INV-004** | Snapshot financeiro pro-rata | Tabela `order_items` sem FK para tabela `products` | Value Object `Money` com Algoritmo do Maior Resto | Alteração de preço/cupom posterior com estorno de 1 item |
| **INV-005** | Ciclo de vida monotônico | Check constraint de status permitidos | Agregado sem setters, métodos de transição estritos | Tentativa de salto de estado ilegal (ex: `PENDING` $\to$ `DELIVERED`) |
| **INV-006** | Encapsulamento modular | Schemas de banco segregados por módulo | Spring Modulith `@NamedInterface` + visibilidade package-private | `ApplicationModules.of(...).verify()` |
| **INV-007** | Equação de reserva de estoque | `CHECK (reserved_quantity <= physical_quantity)` | Agregado `InventoryItem` + `InventoryReservation` com TTL | Expiração de reserva devolvendo saldo disponível |

## 4. Topologia e Isolamento Modular (Spring Modulith)

A aplicação é particionada em módulos com fronteiras de domínio explícitas:

```text
com.trsthales.ecommerce
├── identity/          # Assinatura e validação de RSA JWT, usuários, perfis (RBAC)
├── catalog/           # Produtos, categorias, variações de SKU, busca Full-Text (Postgres FTS)
├── inventory/         # Estoque, bloqueio pessimista, reservas com TTL e reconciliação
├── cart/              # Carrinho volátil (Redis-backed com TTL de 7 dias)
├── orders/            # Agregado Order, Checkout, Snapshot de Itens, Máquina de Estados
├── payments/          # SPI de Provedores, Pagamentos, Webhooks e Reconciliador Ativo
├── promotions/        # Validação de cupons e motor de rateio de descontos
├── shipping/          # Estratégia de cálculo de frete por CEP/peso/dimensões
└── common/            # Kernel Compartilhado (Money VO, SecurityContext, Idempotency, RFC 7807)
```

### 4.1. Regras de Visibilidade e API Pública de Módulo
Para garantir a **INV-006**:
1. Todo módulo expõe apenas classes públicas em seu pacote raiz ou subpacote `api` anotado com `@NamedInterface`.
2. Repositórios JPA, entidades JPA internas e services auxiliares são estritamente **package-private** dentro de subpacotes `internal` ou `infrastructure`.
3. Nenhum módulo injeta o repositório de outro módulo. A comunicação síncrona ocorre exclusivamente via Services públicos da API do módulo; a comunicação assíncrona ocorre via eventos de domínio no Outbox do Spring Modulith.

## 5. Modelo de Domínio e Mecânicas de Engenharia

### 5.1. Value Object `Money` e Distribuição de Restos (Hare-Niemeyer)
Para eliminar qualquer *drift* de centavos em operações multi-etapas (subtotal $\to$ desconto $\to$ frete $\to$ imposto), a representação monetária é encapsulada em um Value Object imutável que implementa o **Algoritmo do Maior Resto (*Largest Remainder Method*)**:

```java
package com.trsthales.ecommerce.common.domain;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.*;
import java.util.stream.IntStream;

public record Money(BigDecimal amount, Currency currency) implements Comparable<Money> {
    public static final Currency BRL = Currency.getInstance("BRL");
    public static final Money ZERO = Money.of(BigDecimal.ZERO);

    public Money {
        Objects.requireNonNull(amount, "Amount é obrigatório");
        Objects.requireNonNull(currency, "Currency é obrigatória");
        if (amount.scale() > 2) {
            amount = amount.setScale(2, RoundingMode.HALF_EVEN);
        }
    }

    public static Money of(BigDecimal amount) {
        return new Money(amount, BRL);
    }

    public static Money of(String amount) {
        return new Money(new BigDecimal(amount), BRL);
    }

    public Money plus(Money other) {
        assertSameCurrency(other);
        return new Money(this.amount.add(other.amount), this.currency);
    }

    public Money minus(Money other) {
        assertSameCurrency(other);
        return new Money(this.amount.subtract(other.amount), this.currency);
    }

    public Money multiply(int quantity) {
        return new Money(this.amount.multiply(BigDecimal.valueOf(quantity)), this.currency);
    }

    /**
     * Distribui o montante proporcionalmente de acordo com os pesos, 
     * garantindo que a soma dos itens seja EXATAMENTE igual ao total original.
     */
    public List<Money> distribute(List<BigDecimal> weights) {
        BigDecimal totalWeight = weights.stream().reduce(BigDecimal.ZERO, BigDecimal::add);
        if (totalWeight.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Peso total deve ser positivo");
        }

        List<BigDecimal> rawAmounts = new ArrayList<>();
        List<BigDecimal> remainders = new ArrayList<>();
        BigDecimal distributedSum = BigDecimal.ZERO;

        for (BigDecimal weight : weights) {
            BigDecimal share = this.amount.multiply(weight).divide(totalWeight, 4, RoundingMode.FLOOR);
            BigDecimal roundedShare = share.setScale(2, RoundingMode.FLOOR);
            rawAmounts.add(roundedShare);
            remainders.add(share.subtract(roundedShare));
            distributedSum = distributedSum.add(roundedShare);
        }

        BigDecimal remainderToDistribute = this.amount.subtract(distributedSum);
        int centsToAdd = remainderToDistribute.movePointRight(2).intValue();

        Integer[] order = IntStream.range(0, remainders.size()).boxed()
            .sorted((i, j) -> remainders.get(j).compareTo(remainders.get(i)))
            .toArray(Integer[]::new);

        for (int i = 0; i < centsToAdd; i++) {
            int idx = order[i];
            rawAmounts.set(idx, rawAmounts.get(idx).add(new BigDecimal("0.01")));
        }

        return rawAmounts.stream().map(a -> new Money(a, this.currency)).toList();
    }

    private void assertSameCurrency(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Moedas incompatíveis: " + this.currency + " vs " + other.currency);
        }
    }

    @Override
    public int compareTo(Money other) {
        assertSameCurrency(other);
        return this.amount.compareTo(other.amount);
    }
}
```

### 5.2. Ciclo de Vida do Carrinho vs. Reserva de Estoque (`INV-002` & `INV-007`)
1. **Carrinho Otimista (Redis):** O carrinho armazena apenas intenções de compra no Redis com TTL de 7 dias. Adicionar itens **não** reserva estoque físico, prevenindo ataques de *Inventory Hoarding*.
2. **Pre-flight Check:** A leitura `GET /api/v1/cart` consulta a visão de leitura do inventário para alertar na UI itens com `available_quantity == 0`.
3. **Reserva no Checkout:** A reserva é acionada no momento da criação do pedido (`POST /api/v1/orders`), gerando um registro `InventoryReservation` com status `ACTIVE` e TTL de 15 minutos.
4. **Locking Pessimista:**
   ```java
   @Lock(LockModeType.PESSIMISTIC_WRITE)
   @Query("SELECT i FROM InventoryItem i WHERE i.sku = :sku")
   Optional<InventoryItem> findBySkuForUpdate(@Param("sku") String sku);
   ```
5. **Compensação por Timeout:** Caso o pagamento não ocorra em 15 minutos, um job de reconciliação dispara `OrderExpiredEvent` via Spring Modulith Outbox, transicionando a reserva para `RELEASED` e recompondo `available_stock`.

### 5.3. Snapshot Histórico do Pedido e Rateio Pro-Rata (`INV-004`)
Para proteger a integridade contábil e viabilizar estornos parciais com precisão matemática:

```java
package com.trsthales.ecommerce.orders.domain;

import com.trsthales.ecommerce.common.domain.Money;
import java.util.UUID;

public record OrderItemSnapshot(
    UUID productId,
    String sku,
    String productTitle,
    Money grossUnitPrice,      // Preço de tabela no instante exato da compra
    Money discountAmount,       // Parcela do cupom/promoção rateada via distribute()
    Money netUnitPrice,         // Preço líquido unitário efetivo (gross - discount)
    Integer quantity,
    Money totalPrice            // (netUnitPrice * quantity)
) {
    public OrderItemSnapshot {
        if (!grossUnitPrice.minus(discountAmount).equals(netUnitPrice)) {
            throw new IllegalStateException("Violação contábil: netUnitPrice != grossUnitPrice - discountAmount");
        }
    }
}
```

### 5.4. Limites Transacionais e Orquestração do Checkout

Para garantir que conexões JDBC não fiquem presas durante chamadas de rede externas, o fluxo de checkout é segregado em **duas transações locais estritas e uma etapa assíncrona**:

```text
[HTTP POST /api/v1/orders] (Idempotency-Key: <UUID>)
       │
       ▼ (TRANSAÇÃO LOCAL 1 - ACID, Duração: ~15ms)
┌─────────────────────────────────────────────────────────────────┐
│ 1. Valida integridade do carrinho e calcula rateio de cupom    │
│ 2. Executa reserva de estoque (INV-002 / INV-007) via SELECT FOR UPDATE│
│ 3. Persiste Agregado Order (Status: PAYMENT_PENDING)            │
│ 4. Persiste Idempotency-Key (Status: COMPLETED com payload)     │
│ 5. Publica OrderCreatedEvent no Outbox (Spring Modulith)        │
└─────────────────────────────────────────────────────────────────┘
       │
       ▼ (FORA DE TRANSAÇÃO JDBC / ASSÍNCRONO)
┌─────────────────────────────────────────────────────────────────┐
│ Chamada de Gateway / Geração de QRCode Pix / Sessão de Checkout │
└─────────────────────────────────────────────────────────────────┘
       │
       ▼ (TRANSAÇÃO LOCAL 2 - Quando Webhook/Confirmação é recebido)
┌─────────────────────────────────────────────────────────────────┐
│ 1. Valida assinatura e idempotência do Webhook (INV-003)        │
│ 2. Executa SQL Condicional de transição de status (INV-001):   │
│    UPDATE orders SET status = 'PAID', version = version + 1     │
│    WHERE id = :id AND status = 'PAYMENT_PENDING'                │
│ 3. Transiciona InventoryReservation para FULFILLED              │
│ 4. Publica OrderPaidEvent no Outbox                             │
└─────────────────────────────────────────────────────────────────┘
```

### 5.5. Motor Universal de Idempotência e Crash Recovery (`INV-003`)
Endpoints críticos (`/orders`, `/payments/checkout`, `/payments/webhooks`) utilizam o header `Idempotency-Key`:

```sql
CREATE TABLE idempotency_keys (
    key VARCHAR(128) PRIMARY KEY,
    payload_hash VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL, -- PROCESSING, COMPLETED, FAILED
    response_code INT,
    response_body JSONB,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    locked_until TIMESTAMP WITH TIME ZONE NOT NULL
);
```

#### Protocolo de Resolução de Idempotência:
1. **Chave Nova:** Insere registro com status `PROCESSING` e `locked_until = NOW() + INTERVAL '2 minutes'` dentro da mesma transação JDBC de negócio.
2. **Chave Concorrente em `PROCESSING` (`locked_until > NOW()`):** Retorna `409 Conflict` ou `425 Too Early`.
3. **Crash Recovery (`PROCESSING` com `locked_until < NOW()`):** O processo anterior caiu antes de comitar. A chave é destravada para recuperação controlada.
4. **Chave `COMPLETED`:** Retorna o payload em cache com header `X-Cache-Lookup: HIT`.

### 5.6. SPI de Pagamentos, Imutabilidade de Payload e Reconciliação

```java
package com.trsthales.ecommerce.payments.domain;

import com.trsthales.ecommerce.common.domain.Money;

public interface PaymentProvider {
    PaymentResult authorize(PaymentRequest request);
    PaymentResult capture(String transactionId, Money amount);
    PaymentResult refund(String transactionId);
    PaymentStatus checkStatus(String transactionId);
}
```

#### Invariante de Imutabilidade de Payload em Webhooks:
- Para o mesmo par `(provider, external_event_id)`, o `payload_hash` é estritamente imutável.
- Se `(external_event_id)` existe e `payload_hash` coincide: descarta duplicata e retorna `200 OK`.
- Se `(external_event_id)` existe e `payload_hash` diverge: rejeita imediatamente com `422 Unprocessable Entity` e dispara alerta de segurança (potencial adulteração).

#### Reconciliador Ativo em Background:
Job agendado via Spring `@Scheduled` busca pagamentos em estado `PAYMENT_PENDING` há mais de 10 minutos e invoca `paymentProvider.checkStatus()` diretamente no gateway, eliminando o risco de pedidos perdidos por falhas de entrega de webhooks.

### 5.7. Propagação Agnóstica de Autenticação (`INV-006`)
Para desacoplar as entidades de segurança do módulo `identity` do restante do sistema:

```java
package com.trsthales.ecommerce.common.security;

import java.util.Set;
import java.util.UUID;

public record AuthenticatedUser(
    UUID userId,
    String email,
    Set<String> roles
) {
    public boolean hasRole(String role) {
        return roles != null && roles.contains(role);
    }
}
```

- O módulo `identity` valida o RSA JWT e popula o `SecurityContextHolder`.
- Qualquer módulo consome o usuário atual através da interface pública `CurrentUserProvider` do módulo `common`.

## 6. Estratégia de Verificação Automatizada

1. **Verificação de Fronteiras Modulares (Spring Modulith):**
   ```java
   @Test
   void verifyModularArchitecture() {
       ApplicationModules.of(EcommerceApplication.class).verify();
   }
   ```
2. **Teste de Concorrência de Estoque (Testcontainers PostgreSQL):**
   - 20 threads simultâneas via `CompletableFuture` tentando comprar a última unidade física de um SKU (`physical_quantity = 1`).
   - Asserção: Exatamente 1 pedido é criado com sucesso (`201 Created`); 19 requisições recebem `409 Conflict`; `available_quantity` final no banco é exatamente `0`.
3. **Teste de Colisão Concorrente de Webhooks (INV-001):**
   - 10 webhooks idênticos disparados em paralelo para o mesmo pedido em `PAYMENT_PENDING`.
   - Asserção: Apenas 1 thread executa a transição de estado para `PAID`; todas as outras 9 recebem `200 OK` (duplicata tratada); exatamente 1 evento `OrderPaidEvent` é gravado no Outbox.
4. **Teste de Exatidão Monetária (INV-004):**
   - Aplicação de cupom de R$ 10,00 sobre 3 itens de R$ 33,33.
   - Asserção: A soma dos descontos rateados pro-rata é rigorosamente R$ 10,00 (dois itens recebem R$ 3,33 e um recebe R$ 3,34); soma total fecha sem desvio de 1 centavo.
